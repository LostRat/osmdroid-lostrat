Vector MBTiles (MVT) as a MapsForge data store

November 16, 2026 · 7.0.3-lostrat-SNAPSHOT · New module osmdroid-mapsforge-mvt, glue in osmdroid-mapsforge, test in TestOsmdroidLostRat. Nothing is committed; a commit plan is at the end.

What it does

An .mbtiles file of Mapbox Vector Tiles in the OpenMapTiles schema (tilemaker output from an OSM .pbf) is opened as a MapsForge MapDataStore. The stock MapsForge renderer and the existing render-theme XML then draw it exactly as they draw a .map file: no new renderer, no theme changes. The Java code follows the Swift MapsforgeVectorTiles module of the OsmMap macOS/iOS app.

Because each file is its own data store, MapsForge's MultiMapDataStore combines them. A base map and a contour file are two stores, and a .map file can be mixed with a vector contour file, so contour lines no longer have to be merged into the .pbf before a .map is written.

Use

MapsForgeTileSource.createInstance(application);          // once

File[] files = { baseMbtiles, contourMbtiles };              // or { portlandMap, contourMbtiles }
Arrays.sort(files);                                          // cache key depends on order
String cacheName = MapsForgeTileCacheKeys.forMapsAndTheme(files, "default-path-contour");
MapsForgeTileSource source = MapsForgeTileSource.createFromFiles(files, theme, cacheName);
source.applyDensityScaling();
mapView.setTileProvider(new MapsForgeTileProvider(new SimpleRegisterReceiver(context), source));

createFromFiles opens any file whose name ends in .mbtiles as vector tiles and everything else as a .map file. An app that already passes its files to createFromFiles needs no other change. A raster .mbtiles file is rejected with an IllegalArgumentException.

Data store and tile cache are two different things

The data store is the source of map features: it stands where the .map file reader stood. The SQLite tile cache (SqlTileWriter) is unchanged and still stores the rendered PNG tiles. The path of a tile is:

memory cache → SqlTileWriter cache (rendered PNG) → MapsForge render ← MultiMapDataStore ← .map / .mbtiles
ConcernChoice
DurabilityThe .mbtiles file is opened read-only and never written, so it cannot be damaged by a crash. Rendered tiles persist in the existing SqlTileWriter database, keyed by file name, size, modification time, theme and scale, so a replaced map file never shows stale tiles.
SpeedA tile is rendered once and then comes from the PNG cache. Decoded source tiles are kept in memory because one z14 tile serves 16 tiles at z16 and 256 at z18, and the label pass reads a 3x3 block for every tile. An area read returns each way once (3,698 ways for a 3x3 block at z16, against 5,466 read tile by tile).
MemoryThe decoded-tile cache is bounded by coordinate count, not tile count: 500,000 coordinates, about 27 MB when full, sized to hold the densest 3x3 block of z14 tiles in central Portland (423,402 coordinates). Tag objects and identical tag lists are shared between ways. The trail cache may add up to half as much. Pass a smaller budget to the MvtMapDataStore constructor to trade speed for memory.
FlickerNothing new is drawn on the map view: tiles go through the same MapsForgeTileProvider as .map tiles, and osmdroid keeps showing the rescaled old tiles while new ones render. See the emulator results below.

How the vector tiles are read

  • Tag mapping. OpenMapTilesTags turns OpenMapTiles layers and attributes back into OSM tags (transportation class path becomes highway=path, the custom contour layer becomes contour_ext=elevation_major|medium|minor with ele, and so on), which is why the themes need no change.
  • Label-only ways. OpenMapTiles carries road names on separate lines (transportation_name). These become LabelOnlyWays: the renderers run only caption and path-text instructions for them. With the plain DirectRenderer the name lines are stroked a second time and fill the gaps of dashed trails (28,781 pixels differ in one z16 test block).
  • Overzoom. Above the file's deepest zoom (14) the ancestor tile is used and only ways meeting the requested tile plus a margin are returned.
  • Trail backfill. Tilemaker's config holds paths and footways only at z14 and tracks from z13, but the theme shows trails from z12. For z12 and z13 the missing trails are taken from the z14 tiles underneath, decoding only the two transportation layers. Off for files without a transportation layer.
  • Points. A POI belongs to the one tile that contains it, with a minimum zoom per kind.
  • Damage. A corrupt tile gives what could be decoded; readMapData never throws.

Module layout

osmdroid-mapsforge-mvt depends on MapsForge only and imports no org.osmdroid class outside its own package, so it can be lifted into a project of its own later. osmdroid-mapsforge depends on it with api, so apps get it without a new dependency line. Its POM licence follows osmdroid-mapsforge (LGPLv3, as it links MapsForge); change osmdroid-mapsforge-mvt/gradle.properties if you want another.

Known limits

  • Labels of cut lines. A river or road cut at tile edges gets a label per piece, so at z12 two can butt together ("Willamette RiveWillamette River"). The Swift app has the same behaviour; joining pieces with equal tags would fix it.
  • Precision above z18. z14 tiles at extent 4096 give one unit per pixel at z18. Contours and buildings look angular at z19 and beyond. This is a property of the data.
  • Custom layers. The buildings-addr and cemetery files use their own schemas and are not mapped yet; full, drop and contour are.
  • Tile size. On Android before API 28 a single tile blob is limited to 2 MB by the cursor window. The largest tile in the test files is 206 KB.
  • Test map. The Portland .map in the test app already contains contours, so the ".map + vector contours" source shows both sets inside Forest Park.
