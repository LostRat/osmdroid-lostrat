This report audits the updated display layer system (the z-index layer ordering, spatial index, hierarchy visibility, and LRU hit-test caching that this fork adds) together with the underlying polyline drawing pipeline in LinearRing, LineDrawer, and PolyOverlayWithIW.

The existing infrastructure is solid: projection results are cached per point-set, bounding boxes are precomputed, off-screen overlays are culled before drawing, and hardware acceleration is in play. The findings below are targeted improvements layered on top of that foundation — not a rewrite.

Two themes dominate. First, redundant per-frame work in the overlay draw loop: DefaultOverlayManager.drawWithLayers() re-sorts a fixed 10-value enum and re-scans the full overlay list on every single frame. Second, and more impactful at scale, per-polyline object allocation: LinearRing.clipAndStore() allocates fresh PointL objects on every draw. At 600 polylines × 60 fps that is on the order of 100,000+ short-lived allocations per second, directly driving the GC pauses that show up as scroll/zoom jank.

The six "quick wins" are isolated, low-risk changes with no behavioral side effects and can ship together in a single PR. The remaining structural and architectural items deliver further gains but warrant their own review.

02 What's Already Working

The pipeline already implements a strong set of optimizations. These should be preserved — the recommendations that follow build on them.

  • mProjectedPrecomputed flag — GeoPoint→Mercator conversion cached per point-set
  • BoundingBox precomputed once in computeProjected()
  • Spatial index grid (256 px cells) with adaptive threshold for tap detection
  • isVisible() circle-overlap viewport cull before drawing
  • SideOptimizationPointAccepter — removes same-X / same-Y collinear points
  • compact() in LineDrawer — drops degenerate zero-length segments
  • Hardware acceleration via MapView.setLayerType
  • LRU hit-test cache (sHitTestCache) in PolyOverlayWithIW
  • Pre-allocated mVisibility* scratch fields (no allocation in isVisible)
  • drawWithLines() batches segments into one Canvas.drawLines() call

04 Findings In Detail

Critical

F1Redundant enum sort on every draw frame

DefaultOverlayManager.java : 285–286

Description

drawWithLayers() runs OverlayLayer.values() — which allocates a fresh array — then Arrays.sort() with a comparator lambda, on every frame.

Root Cause

OverlayLayer is a fixed enum of 10 values whose z-index ordering never changes at runtime. The array allocation and comparison-based sort produce an identical result every time, yet the work (plus a comparator object) is repeated 60×/second.

Estimated Impact

Eliminates a per-frame array allocation, a sort, and a lambda allocation. Small CPU saving but trivially free; removes constant minor GC churn.

F2Per-draw PointL allocation in clipAndStore()

LinearRing.java : 377–379

Description

clipAndStore() declares three new PointL() objects (projected, point, first) as method-locals. This method runs once per polyline per draw, inside the hot path of both drawWithLines() and drawWithPath().

Root Cause

LinearRing is a long-lived object, but these scratch points are recreated each draw. At 600 polylines × 60 fps that is ~108,000 allocations/second from this method alone — the dominant source of GC pressure in polyline-heavy maps.

Estimated Impact

Removes the single largest allocation hotspot. Directly reduces GC pause frequency, the primary cause of visible scroll/zoom stutter.

F4Unconditional full-list fallback scan every frame

DefaultOverlayManager.java : 306–314

Description

After drawing all layers, a fallback loop iterates the entire mOverlayList and calls mOverlayToLayer.containsKey(overlay) for each, to catch overlays not assigned to a layer.

Root Cause

In the common case every overlay is assigned to a layer (assignment is automatic in add()), so this loop performs N map lookups every frame and draws nothing. The work scales linearly with overlay count and is pure waste when no unassigned overlays exist.

Estimated Impact

Eliminates O(n) hash lookups per frame for the typical configuration. Meaningful with hundreds of overlays.

F7Thread-safe containers for UI-thread-only data

DefaultOverlayManager.java : 89–90, 102

Description

mLayeredOverlays and mOverlayToLayer are ConcurrentHashMap; each per-layer list is a CopyOnWriteArrayList.

Root Cause

Overlay add/remove and drawing both occur on the UI thread. ConcurrentHashMap carries synchronization overhead, and CopyOnWriteArrayList copies its entire backing array on every mutation — expensive if overlays are added in bulk. ArrayMap + ArrayList are faster for this access pattern.

Estimated Impact

Lower per-mutation cost and read overhead. Requires verifying no off-UI-thread mutation before changing — hence not a quick win.

F10No distance-based simplification at low zoom

SideOptimizationPointAccepter.java / LinearRing

Description

The only point reduction is SideOptimizationPointAccepter, which collapses runs of identical-X or identical-Y points after clipping. There is no zoom-aware geometric simplification.

Root Cause

At low zoom, many distinct geographic points project within a single pixel of one another. They survive clipping and are each fed to drawLines/Path. A 10,000-point GPS track at zoom 10 may render hundreds of points that contribute nothing visible.

Estimated Impact

For dense tracks viewed zoomed-out, a Ramer–Douglas–Peucker (or greedy 1-px epsilon) pass can cut path length 90%+. Negligible for short polylines. Behavioral change to rendering fidelity — must be zoom-gated and opt-in.

05 Recommended Fixes — Quick Wins

These six changes are isolated, behavior-preserving, and low-risk. They can ship together in one PR.

F1 — Cache the sorted layer array

Before

// drawWithLayers(), runs every frame
OverlayLayer[] layers = OverlayLayer.values();
Arrays.sort(layers,
  (a, b) -> Integer.compare(a.getZIndex(), b.getZIndex()));
for (OverlayLayer layer : layers) { ... }

After

// class-level, sorted once at load time
private static final OverlayLayer[] SORTED_LAYERS;
static {
    SORTED_LAYERS = OverlayLayer.values();
    Arrays.sort(SORTED_LAYERS,
      (a, b) -> Integer.compare(a.getZIndex(), b.getZIndex()));
}
// drawWithLayers():
for (OverlayLayer layer : SORTED_LAYERS) { ... }

Safe: enum values and their z-index are immutable, so the sorted order is deterministic and identical every frame.

F2 — Promote clipAndStore scratch points to fields

Before

private void clipAndStore(...) {
    ...
    final PointL projected = new PointL();
    final PointL point     = new PointL();
    final PointL first     = new PointL();
    for (...) {
        projected.set(...);
        ...
    }
}

After

// reused instance fields on LinearRing
private final PointL mClipProjected = new PointL();
private final PointL mClipPoint     = new PointL();
private final PointL mClipFirst     = new PointL();

private void clipAndStore(...) {
    for (...) {
        mClipProjected.set(...);
        ...
    }
}

Safe: PointL is a mutable value holder used only within the synchronous draw call; promoting to fields just reuses the buffer. clipAndStore is never re-entrant on a single LinearRing. Highest-value fix in the report.

F3 — Reuse the offset point in buildLinePortion

Before

void buildLinePortion(Projection p, boolean store) {
    ...
    final PointL offset = new PointL();
    getBestOffset(p, offset);
    ...
}

After

private final PointL mBuildOffset = new PointL();

void buildLinePortion(Projection p, boolean store) {
    ...
    mBuildOffset.set(0, 0);
    getBestOffset(p, mBuildOffset);
    ...
}

Safe: same rationale as F2 — single synchronous use per draw.

F4 — Guard the fallback loop with a flag

Before

// end of drawWithLayers() — every frame
for (final Overlay overlay : mOverlayList) {
    if (overlay != null && overlay.isEnabled()
        && !mOverlayToLayer.containsKey(overlay)) {
        ...draw...
    }
}

After

private boolean mHasUnassignedOverlays = false;
// set true in add() when an overlay isn't layer-assigned;
// recompute on remove()

if (mHasUnassignedOverlays) {
    for (final Overlay overlay : mOverlayList) {
        if (overlay != null && overlay.isEnabled()
            && !mOverlayToLayer.containsKey(overlay)) {
            ...draw...
        }
    }
}

Note: keep the flag in sync wherever overlays are added/removed/assigned. If assignment is always automatic, the flag stays false and the loop is skipped entirely.

F5 — Cache the paint-list wrapper by identity

Before

public void setPaint(final Paint pPaint) {
    setPaint(new MonochromaticPaintList(pPaint));
}

After

private Paint mCachedPaint;
private MonochromaticPaintList mCachedPaintList;

public void setPaint(final Paint pPaint) {
    if (pPaint != mCachedPaint) {
        mCachedPaint = pPaint;
        mCachedPaintList = new MonochromaticPaintList(pPaint);
    }
    setPaint(mCachedPaintList);
}

Safe: identity (!=) comparison; if a caller mutates a Paint in place without swapping the reference, the wrapper still points at the same live Paint, so rendering stays correct.

F6 — Compute screenRadius once per frame

Before

private boolean isVisible(Projection p) {
    ...
    final double screenRadius = Math.sqrt(
        Distance.getSquaredDistanceToPoint(
            0, 0, screenCenterX, screenCenterY));
    return distanceBetweenCenters <= radius + screenRadius;
}
// called per-polyline in draw()

After

private boolean isVisible(Projection p, double screenRadius) {
    ...
    return distanceBetweenCenters <= radius + screenRadius;
}

// in draw(), compute once before the polyline loop:
final double screenRadius = Math.sqrt(
    Distance.getSquaredDistanceToPoint(
        0, 0, p.getWidth() / 2, p.getHeight() / 2));

Note: since draw() is called per-overlay by the manager, the cleanest realization is to cache screenRadius on the projection (or a per-frame holder) keyed by its version, so each overlay reuses it. Keep radius and distanceBetweenCenters per-polyline.

06 Recommended Fixes — Structural

Higher value or wider blast radius; each deserves its own review and thread-safety audit.

F7Right-size the overlay containers

Before

new ConcurrentHashMap<OverlayLayer, List<Overlay>>();
new ConcurrentHashMap<Overlay, OverlayLayer>();
// per layer:
new CopyOnWriteArrayList<>();

After

new ArrayMap<OverlayLayer, List<Overlay>>();
new ArrayMap<Overlay, OverlayLayer>();
// per layer:
new ArrayList<>();

Prerequisite: confirm all overlay add/remove and draw operations happen on the UI thread. If any background mutation exists, keep concurrent structures or synchronize explicitly. The main mOverlayList may need to stay CopyOnWriteArrayList if iterated during async tile callbacks.

F8Cache isHierarchyEnabled()

Add a boolean mCachedHierarchyEnabled (and a dirty flag) to Overlay. Recompute lazily only when setEnabled() or setParent() is called on the overlay or an ancestor. Because children hold a parent reference, invalidation must propagate downward — simplest is a monotonically increasing "structure version" on the manager that each overlay compares against, recomputing on mismatch.

Risk: cache-invalidation bugs cause overlays to wrongly appear/disappear. Add unit tests for nested FolderOverlay enable/disable before merging.

F9Memoize isVisible() by projection version

Store mLastVisibleProjectionVersion and mLastVisibleResult on PolyOverlayWithIW. Skip the recompute when the projection version matches and the polyline's points are unchanged. This pairs naturally with the per-frame screenRadius plumbing from F6 and with MapView's existing projection-versioning infrastructure (mProjectionVersion).

Risk: requires a trustworthy projection version that bumps on any viewport change (scroll, zoom, rotation, size). Reuse MapView's existing version counter rather than inventing a new one.

07 Architectural Recommendation

F10Zoom-aware point simplification (Douglas–Peucker)

The current chain only removes axis-aligned collinear points. It does not address the dominant cost for dense tracks at low zoom: many points projecting within a pixel of each other.

Proposed Approach

Introduce a composable ZoomSimplificationPointAccepter that wraps the existing SideOptimizationPointAccepter in the accepter chain used by LinearRing.clipAndStore(). It computes a pixel-distance epsilon from the current zoom and discards intermediate points whose screen distance to the last accepted point falls below it. Start with a cheap greedy 1-px pass; upgrade to full Ramer–Douglas–Peucker if fidelity demands it.

// Sketch — greedy epsilon accepter in the org.osmdroid.util chain
public class ZoomSimplificationPointAccepter implements PointAccepter {
    private final PointAccepter mNext;     // e.g. SideOptimization...
    private final double mEpsilonSq;        // (pixels)^2, from zoom
    private long mLastX, mLastY;
    private boolean mHasLast;

    @Override public void add(long x, long y) {
        if (mHasLast) {
            final long dx = x - mLastX, dy = y - mLastY;
            if ((double)(dx*dx + dy*dy) < mEpsilonSq) return; // drop
        }
        mLastX = x; mLastY = y; mHasLast = true;
        mNext.add(x, y);
    }
}

Constraints

  • Opt-in & zoom-gated: default off to avoid changing existing apps' rendering. Enable only below a configurable zoom threshold.
  • Preserve endpoints: always keep first/last points and any milestone-relevant vertices.
  • Placement: belongs in the screen-space accepter chain (after projection, before clip-store) so the epsilon is in pixels, not degrees.
  • Interaction: hit-testing already works in screen space, so simplified geometry stays consistent with taps.

Payoff: for a 10,000-point track at zoom 10, expect a 90%+ reduction in points fed to drawLines — turning a per-frame bottleneck into a non-issue, while being invisible to the eye at that zoom.

How to measure the improvements
  • Frame time: enable Configuration.getInstance().setDebugMapView(true) and read the dispatchDraw timing log; or use Android Studio Profiler → CPU → System Trace and inspect the dispatchDraw / onDraw slices.
  • GC pressure (F2/F3/F5): Memory Profiler → record allocations during a continuous pan over 600+ polylines; count PointL / MonochromaticPaintList allocations and GC events before vs. after.
  • Jank: adb shell dumpsys gfxinfo <package> for janky-frame percentage and the histogram of frame durations.
  • Repro scenario: the polyline sample fragment under OpenStreetMapViewer, loaded with 600+ polylines, panned and pinch-zoomed continuously for ~30s.
