Prepared polyline batches

September 11, 2026 · 7.0.3-lostrat-SNAPSHOT · Library implementation; first consumer is PDXWalk's profile line renderer (see Consumer integration).

Problem and resulting behavior

Adding thousands of road/path polylines one at a time copies the main and layer backing arrays repeatedly. Constructing geometry and installing it all in one UI callback can block input. Applications can now construct detached polylines and an ordered batch on a worker, then attach and publish that batch on the UI thread.

API

APIPurpose / thread
new Polyline() or subclass super(null)Prepare a private polyline without map or info-window access on the worker.
PolylineBatch.Builder.add(polyline, layer).build()Worker: snapshot membership and per-layer order, reject nulls, duplicates and folder members.
Polyline.attachToMap(map) / batch.attachToMap(map)Main thread: initialize density and absent default info windows; preserve geometry, styling and custom info windows.
manager.replacePolylineBatch(previous, replacement)Main thread: validate membership, bulk replace main/layer entries, update layer lookup and clear spatial caches.
PolylineBatch.empty()Initial previous value or replacement that removes all lines owned by this batch.

Integration example

The example is a template: LineData, inputSnapshot, lifecycle checks and executor belong to the consuming application. Capture independent data; do not pass mutable live cache collections to the worker.

// UI-owned fields:
private PolylineBatch displayed = PolylineBatch.empty();
private long generation;

// UI thread: capture display settings and independent input data before starting.
final long request = ++generation;
executor.execute(() -> {
    PolylineBatch.Builder builder = new PolylineBatch.Builder();
    // Add roads first, then paths, for paths to draw above roads in the same layer.
    for (LineData row : inputSnapshot) { // Application-defined immutable input.
        Polyline line = new Polyline(); // Subclasses can call super(null).
        line.setPoints(row.points());
        line.getOutlinePaint().setColor(row.color());
        line.getOutlinePaint().setStrokeWidth(row.width());
        line.setTitle(row.title());
        line.setId(row.id());
        builder.add(line, DefaultOverlayManager.OverlayLayer.INTERACTIVE_BACKGROUND);
    }
    PolylineBatch prepared = builder.build();
    map.post(() -> {
        if (request != generation || isDestroyed() || isFinishing()) return;
        prepared.attachToMap(map);
        DefaultOverlayManager manager = (DefaultOverlayManager) map.getOverlayManager();
        manager.replacePolylineBatch(displayed, prepared);
        displayed = prepared;
        map.invalidate();
    });
});

// UI thread: hide lines and reject any pending background result.
++generation;
manager.replacePolylineBatch(displayed, PolylineBatch.empty());
displayed = PolylineBatch.empty();
map.invalidate();

Ownership, ordering and lifecycle

  • The worker must stop modifying the polyline objects after handing them to the UI. Batch membership is immutable; the objects themselves remain mutable. Reused live polylines must not be edited by a worker.
  • A batch owns only its explicitly supplied top-level polylines. Do not independently remove them or place them in folders. Do not share polylines between maps. Previous members missing from the main list and new members already installed elsewhere in the manager are rejected before list changes.
  • Existing, unrelated overlays retain their relative order. Replacement members are appended above survivors within each chosen layer; batch insertion order applies when layers are disabled. Higher layers still draw last and receive tap priority.
  • Layer lists are updated in the same main-thread callback as the main list and lookup. This is coherent for main-thread drawing/tapping; it is not a transaction for background readers. Existing manager mutation APIs must also be used on the UI thread.
  • Publication does not invalidate automatically and removal does not call onDetach, matching ordinary remove. Close an open info window explicitly before retiring its owner if appropriate. Normal map teardown remains responsible for its repository.
  • Increment the app generation when profile selection, viewport requirements or display filters change, and when hiding/destroying the display. Discard stale worker results before attachment.

Performance and limits

Batch preparation and geometry conversion run in the background. Publication remains linear in the existing overlay count plus old/new batch size. The main list and each layer use bulk removeAll with a hash set and bulk addAll: at most two backing-array copies per list, independent of batch size. There is still per-object lookup/attachment work and temporary memory for the old/new geometry. This is not an O(1) collection swap.

Actual projection, drawing and hit-testing remain on the UI thread. No ANR elimination or device speedup is claimed without app measurements. Time preparation, attachment/publication and the first redraw separately on the affected device and emulator.

Consumer integration

PDXWalk consumes the API in vectordata/BreadcrumbBatchRenderer, driven by its existing BreadcrumbTasksThreadedExec worker. The UI captures the currently installed profile polylines as the previous batch, the worker builds missing polylines with a null MapView through the app's existing draw-item builders, reuses live polylines by id, orders roads, walking routes, simple lines and bicycle routes, and builds the replacement. The UI re-checks its snapshot (mode, display state, zoom, full-precision center, installed lists, profile generation), attaches only newly built polylines, calls replacePolylineBatch(previous, prepared) once and invalidates. Clearing goes through replacePolylineBatch(current, PolylineBatch.empty()). Batch is PDXWalk's default in all builds; the legacy per-polyline path is selectable only in debug builds.

Emulator results: PDXWalk's instrumented BreadcrumbBatchRendererTest (geometry and style parity with the legacy builders, reuse, clearing, an unrelated overlay preserved, 400 repeated cache loads) passed on emulator-5554. A 72 minute Powell Butte session on the Pixel 9 emulator ran in batch mode on 2026-09-11 and exported its event bundle and subsegment route normally. Timing lines from that session were not retained.
